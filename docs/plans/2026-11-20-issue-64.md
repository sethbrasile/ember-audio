# Issue 64 implementation plan

A newly created sound must accept gain and pan changes immediately. A sampler must be able to play it in the same call stack, including in apps that enable `default-async-observers`. Keep the existing Ember peer range (`^3.8.0 || ^4.0.0`) and public routing API. [Issue 64](https://github.com/sethbrasile/ember-audio/issues/64)

## Implementation

1. Reproduce the failure in the dummy app with `EMBER_OPTIONAL_FEATURES='{"default-async-observers":true}' npm run test:ember`. Add regression tests for immediate sampler playback and direct routing edits. Capture the started source and verify it still receives the next stop after Ember settles.
2. In `addon/mixins/connectable.js`, register a synchronous observer on `connections.[]` during `init` and remove it during destruction. Assigning the default array and editing an existing array both trigger wiring. Preserve the call to `wireConnections()` at playback because a Web Audio source can only start once.
3. In `addon/classes/oscillator.js`, let assigning the completed connection array trigger the initial wiring. Count source creations to check that construction wires once and the first play creates a fresh source.
4. Run the full suite on Ember 4.10 with both observer defaults. Exercise released 3.x and 4.x runtimes, including the 3.8 package floor and the 3.28 README baseline. Record which checks use a consuming app, the full suite, or a focused runtime test.
5. Exercise the async default in CI alongside the existing synchronous tests. Remove the resolved warning from the README after verification.
6. Pack the addon and load it outside the checkout. The original package entry point required a development-only coverage plugin during every consumer build. Load it only in the addon's own project and confirm that its CI coverage run still instruments the routing code.

## Verification

- Before the fix, 11 of 104 Chrome tests failed on Ember 4.10.0 with async observers, including immediate sampler playback and custom routing. After the fix, all 104 passed with either observer default. The coverage run also recorded execution of the routing mixin.
- Ember 3.8.3 passed all 104 tests with its synchronous observers. Ember 3.28.12 and 4.12.4 passed all 104 in each mode. The 3.28 async scenario also passed on CI's Node 14.21.3. Its test runner needs Testem 3.10.1 because ember-try skips the lockfile and newer Testem releases fail during startup on that Node version.
- The other six legacy LTS scenarios each passed all 104 tests on Node 14.21.3 in Chrome: Ember 3.12.4, 3.16.10, 3.20.7, 3.24.7, 4.4.5, and 4.8.6.
- Focused Chrome checks passed in 34 configurations across 18 published Ember runtimes from 3.8.0 to 4.12.4. They exercised immediate gain and pan, routing edits, sampler output in both channels, source identity after observers settle, oscillator initialization, and destruction.
- An independent Ember CLI 3.28.6 app installed the packed addon with Ember 3.28.12 and built without the coverage plugin. Chrome confirmed the app's default observer was asynchronous. In that build the addon immediately applied gain and pan, exposed an inserted effect, and rendered nonzero sampler output on both channels.
